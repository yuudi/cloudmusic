# Cloud Music

Cloud Music 是一个开源音乐平台。用户可以在线聆听自己创作或购买的歌曲，也可以分享音乐给好友。

本文描述整体设计，版本范围见根目录的[路线图](../README.md#路线图)。0.1 实现个人播放，好友与分享功能安排在 0.2。

## 用户与好友

- 支持标准登录和注册流程，也允许游客使用。
- 游客是临时用户，可以添加好友、播放公开歌曲，也可以进入分享会并按房间规则播放歌曲。连接网盘之前必须设置密码，成为正式用户。
- 游客连续 30 天不活跃后清理临时账号。活跃时间的更新及关联记录的清理细节后续设计。
- 普通好友关系需要双方确认。好友分组仅供用户查看，不影响歌曲权限。
- 邀请用户进入分享会需要好友关系；进入房间后，参与者自动成为好友，并归入“一起听过歌”分组。该好友关系在分享会结束后仍然保留，用户可以主动删除好友。暂不支持拉黑。

## 歌曲、歌单与存储

- 用户主动导入歌曲，不自动扫描存储空间。用户可以连接自己的网盘、S3、WebDAV 或 FTP 等存储，也可以使用独立的 Cloud Music 存储服务。
- 首批支持 S3、WebDAV、Google Drive 和 OneDrive，使用 rclone 统一接入；其他存储后续按能力验证后扩展支持。
- 不同用户分别导入的歌曲视为不同资源；保存其他用户的歌曲时，视为同一个资源。一首歌曲可以有多个所有者，并存在于多个网盘。
- 保存操作有时也叫转存：将歌曲文件保存到当前用户的默认网盘。没有连接网盘的用户不能保存歌曲。保存后的歌曲属于当前用户，可以加入其歌单；具体权利取决于分享者设置。
- 当前按（歌曲、保存者）限制同一用户只能成功保存同一歌曲一次。已有成功保存记录时，即使换一个分享者或切换默认网盘，也不允许第二次保存；暂不合并或升级不同分享者授予的权利。失败任务可以重试，不算第二次成功保存。未来允许再次保存，具体规则后续设计。
- 保存失败时清理本次操作产生的残留文件，更多细节后续另文说明。
- 保存操作的并发控制采用数据库短事务和锁，配合唯一约束原子创建或认领保存任务；重复请求返回已有任务或副本的状态。网络复制在事务外执行，不在整个传输期间持有数据库锁。具体唯一键、任务恢复与失败清理细节后续另文说明。
- 个人播放时，播放者转存过歌曲就只读取自己保存的文件，否则只读取分享者的文件。分享会是例外：由服务端统一读取房间选定的一个来源，并向所有参与者分发，不按参与者各自保存的副本分别读取。
- 导入歌曲时限制文件格式和码率，首版只考虑最通用的几种格式，具体支持范围待定。导入时不转码。
- 歌单只能包含一个用户的歌曲。分享歌单时不检查歌曲权限，在播放或保存时逐首检查。
- 歌曲文件被删除、网盘断开或其他原因导致文件来源不可读取时，第一次失败即显示“连接失败”。界面保留歌曲记录和来源位置，不自动从列表中移除。
- 服务端按文件来源分别记录读取失败的时间和次数，并自动重试。重试时间暂定为首次失败后立即、10 分钟、1 小时、1 天和 7 天，共 5 次，不含首次读取失败。重试期间显示“连接失败”，最后一次重试失败后显示“已失效”；重试成功后恢复正常。
- 用户可以手动重试、更换来源或重新导入。即使显示“已失效”，仍保留原来源位置；只有用户点击删除时，才将歌曲从列表中移除。
- 存储和流量费用由对应存储空间的所有者承担。

### 播放器

标准音乐播放器支持个人歌单和好友歌单，也支持分享会：多个好友同时播放，并同步时间轴。0.1 先实现个人听歌，0.2 再实现好友与分享相关功能。

个人播放允许拖动进度。播放器需要支持范围读取和按时间定位，具体实现仍需验证。

分享会包括歌单、点歌和轮播三种模式。房间操作总体采用投票制度，已确认的同步规则及后续控制设计见[分享会](party-mode.md)。

播放器支持预加载，具体预加载逻辑待定。

### 歌曲权限

权限按（歌曲、所有者）设置，同一首歌曲的不同所有者分别拥有独立的权利和分享设置，尽量保持简单：

- 本人可以播放自己导入的所有歌曲。
- 导入时用户必须自行声明歌曲权利，平台不进行验证：
  - **播放权**：可以自行播放，并允许开启好友播放权限。
  - **所有权**：完全所有权，可以传播，允许开启所有权限。
- 播放和保存权限可以授予好友或平台所有用户。
- 歌曲权限和分享权限是不同的权限。即使用户拥有某歌曲所有权，也可以将其设置为不允许他人保存。
- 保存时，分享者可以设置保存者继承所有权，或者仅获得播放权。只有分享者允许继承所有权时，保存者才获得所有权。
- 保存成功后，保存者取得的权利独立于原分享者。即使原分享者之后撤销分享或删除文件，保存者仍可按保存时取得的权利继续播放和分享。当前不实现授权撤销（revoke）机制；数据库设计应考虑保留保存来源和授权信息，便于未来扩展。
- 以“仅播放”权限保存的歌曲，与用户自行导入并声明为播放权的歌曲一样。多个用户保存同一首歌曲时，共享歌曲资源信息（例如封面），各自的文件和权利独立。

下表说明每种歌曲权利允许开启的分享能力上限。“可开启”不代表默认开启，实际访问仍取决于该所有者的分享设置。只有播放权时，不允许开启面向平台所有用户的播放，也不允许他人保存。

| 能力 | 仅播放权 | 所有权 |
| --- | --- | --- |
| 本人播放 | 允许 | 允许 |
| 允许好友播放 | 可开启 | 可开启 |
| 允许平台所有用户播放 | 不允许 | 可开启 |
| 允许好友保存 | 不允许 | 可开启 |
| 允许平台所有用户保存 | 不允许 | 可开启 |
| 保存时授予保存者播放权 | 不允许发起保存分享 | 可设置 |
| 保存时授予保存者所有权 | 不允许 | 可设置 |

允许保存时，保存者只能获得播放权或所有权之一。获得播放权后仍可按上表允许好友播放；获得所有权后可自行决定是否开启播放和保存分享。两者均不受原分享者之后撤销分享的影响。

## 服务架构

- 客户端采用 Svelte，同时兼容移动端和桌面端的响应式设计。UI 和业务逻辑尽量复用，音频播放能力优先使用浏览器解码，若失败则回退到 ffmpeg wasm 解码器。
- 服务端采用 Go，在项目内部封装自己的存储接口，通过 rclone Go 库访问各存储后端，固定依赖版本，避免业务代码直接依赖各后端实现。
- 初期面向自托管、单机部署；遵循 12-factor，便于未来部署到 Kubernetes。Redis 是确定使用的基础组件，具体职责随技术设计细化。
- 配置通过环境变量注入，数据库和 Redis 等作为外部依赖接入；日志输出到标准输出和标准错误，进程支持优雅退出。
- 歌曲、权利、分享设置、存储连接和需恢复的任务信息持久保存于数据库。存储服务凭据和 OAuth 令牌加密保存；进程重启后可以恢复任务，具体任务恢复机制待设计。
- 主服务不承担歌曲音频文件的持久存储职责，但允许保留可随时清理、重新获取的音频缓存。音频链路为：网盘 → 服务端边读取、边缓存、边转发 → 客户端，无需等整首下载完成再播放。
- 服务端转发产生的带宽等费用由服务端承担。
- 主服务保存歌曲元数据和封面等信息，并使用自己的 S3 存储封面。
- Cloud Music 存储空间是与本体分离的可选独立服务，用于保存少量未连接网盘的用户手动上传的歌曲。该服务不接受保存/转存写入，使用它不满足“转存到默认网盘”的条件；未连接外部网盘的用户仍不能转存其他用户的歌曲。这个存储空间与封面使用的存储空间不同。
- 使用 Cloud Music 存储的用户不活跃一段时间后，清理其在该服务中存放的歌曲；具体不活跃期限及清理细节待定，与游客账号的 30 天不活跃清理规则分别定义。
- 封面只从歌曲文件中读取，不支持修改。源文件包含封面或预览时予以展示；没有时使用占位符。
- 服务端不转码。仅在播放时根据客户端对文件格式的支持情况，由客户端按需转码播放；转码结果不持久保存。

### 存储接入

- 每个用户的存储连接配置、凭据和 OAuth 令牌独立管理；刷新后的令牌应持久保存，并验证并发刷新时的正确性。
- Google Drive 和 OneDrive 的 OAuth 授权流程、应用配置和权限范围需单独验证，包括自托管部署时由谁配置 Client ID 和相关密钥。
- rclone 统一底层接口，各存储的读取、范围读取、写入、复制及文件标识能力仍需分别验证，不默认所有后端能力完全一致。
- 明确 rclone 内部短期重试与平台长期重试的边界，避免重试叠加导致播放请求长时间阻塞。

### 音频缓存与转发

- 时间过期默认启用，过期时间按“最后一次读取时间 + 歌曲时长 + 额外保留时间”计算，其中额外保留时间默认 60 分钟，可配置。允许关闭时间过期，关闭后不设时间上限，仅按磁盘容量和 LRU 淘汰。
- 缓存设置包括额外保留时间（默认 60 分钟，允许设置为无限）、缓存总容量上限（默认 10GB，允许设置为无限）和磁盘预留空间（默认 10GB 且必须设置），三者共同决定缓存保留与淘汰。达到时间期限时过期；缓存总量超限或磁盘剩余空间不足预留值时，按 LRU（Least Recently Used，最近最少使用）淘汰可清理缓存。正在读取的缓存不在读取过程中删除。
- 缓存使用可丢弃的临时磁盘空间；缓存缺失时重新读取源文件，业务正确性不依赖本地缓存跨进程重启或跨实例持续存在。Redis 可用于缓存索引和协调，音频内容存放于临时缓存层。
- 缓存按具体存储连接及文件标识或路径区分，不只按歌曲资源标识区分，避免混用不同所有者的副本。源文件变化采用宽松校验：访问来源时，只要文件大小和歌曲时长均未改变，就认为文件未变化，不要求内容哈希或严格版本校验；任一发生变化时，旧缓存失效，已缓存区间不能与新文件内容拼接。
- 缓存命中按请求区间判断：未过期且所需区间已完整写入并可读取时，直接从缓存播放，不为每次命中额外访问或检查来源。源文件删除、网盘断开或存储授权失效后，已有可用缓存仍可播放；只在缓存未命中或补齐缺失区间时访问来源，并按既有规则处理读取失败。
- 缓存状态需区分正在下载、部分区间可用、完整和失败。部分缓存只能服务已经完整写入的区间，缺失区间按需读取来源；不能仅凭缓存文件存在或文件长度判断所需区间已缓存。
- “相同来源并发”指多个请求同时读取同一个存储副本。后续对相同或重叠区间的请求合并上游读取并复用缓存，避免缓存未命中时重复拉取；不同偏移的请求按需补齐缺失区间。该能力属于性能优化，首版可让请求独立读取上游，不以实现读取合并作为正常运行的前提；并发缓存写入仍须保证正确性。
- 分享会复用统一的上游读取和缓存，向多个参与者分发；中途加入和断线恢复时按偏移读取缓存，必要时补齐缺失区间。
- 命中缓存时仍按对应个人播放或分享会的权限规则进行鉴权。
- 编写缓存命中与读取逻辑时，应便于调整缓存保留时间、关闭时间过期及复用有效缓存，不写死保留时长，也不将缓存时效与文件有效性混为一谈。

### 待验证与后续事项

- 明确首版音频格式及编码清单，验证 Android、iOS 和目标浏览器中的直接播放能力；客户端临时转码的可行性仍需验证。
- 验证移动端后台连续播放、锁屏控制、耳机操作、音频焦点及来电打断；浏览器和 PWA 的能力分别验收。
- 验证播放器与服务端的 HTTP Range、拖动进度、按时间自动定位和断线恢复能力。
- PWA 的离线支持、Service Worker 缓存和更新策略后续单独设计。
- 数据模型需明确歌曲资源、所有者持有记录、存储副本，以及保存来源与授权信息之间的关系，为未来授权撤销扩展保留空间。
- 未来允许同一用户再次保存同一歌曲，包括从不同分享者保存或切换默认网盘后保存；多副本、权利合并或升级及重复保存的规则尚未设计，当前统一拒绝第二次保存。
- 缓存后续优化：合并相同来源的并发上游读取、延长缓存保留时间，以及仅按磁盘容量和 LRU 淘汰的策略。
- 部分缓存的区间记录、并发写入和失败恢复机制需具体设计；进程重启后是否复用残留缓存及如何校验待设计。
- 缓存容量边界待定：单文件超过缓存上限、无法满足磁盘预留空间或缓存写入失败时，是否降级为不写缓存的在线转发。
